Iteration 6 — reciprocal transport controls and a production counterexample
==========================================================================
Objective: beat Ghostty on every metric without breaking correctness or latency.
Outcome: concrete new causal evidence, no accepted runtime optimization, not an
all-metric championship. No acceptance command is bound to this loop.

New finding: placement effects survive removal of the terminal
-------------------------------------------------------------
New bench/linux/transport-control.py reuses the AST statements that build the
existing tput.py workloads at 154x39. It does not execute terminal setup or
rewrite the workload bytes. Three workloads (ASCII, Unicode, scroll-region) use
fixed 64-KiB writes to /dev/null, a pipe, or a raw PTY. Pipe/PTY feed a minimal C
reader with no parser, renderer, DA1, scrollback, compositor or terminal window.
The C sink validates byte totals, reports actual allowed CPUs, retries EINTR,
and timestamps completion before formatting the result.

Nine transport/producer treatments are shuffled per block, 12 blocks per run.
Three complete runs contain 972 measured trials (324 each), with all trial rows,
orders, masks, byte counts, hashes and summaries retained. Separate smoke runs
are not included in those 972. The sink is placed on large or small L3; producer
arms are unrestricted, large L3 (0-7,16-23), small L3 (8-15,24-31). These are this
9950X3D's masks, not portable defaults. Masks do not identify the particular core
used. Host load/frequency were not isolated.

Paired median raw-PTY throughput ratios vs unrestricted producer in each run:

  Reader domain / producer       ASCII       Unicode     Region
  large / small, seed 179365     .3560 2/12  .4271 1/12  .3401 3/12
  large / small, seed 179366     .3697 1/12  .4405 0/12  .4328 2/12
  small / small, seed 179367     .9950 4/12  .9963 5/12  1.0105 7/12
  small / large, seed 179367     .8470 0/12  .8465 1/12  .8231 0/12

Entries after ratios are throughput wins out of 12 blocks. Exploratory sign
tests are two-sided and uncorrected for multiple metrics. Large-reader
replication small-producer p: .00635/.000488/.03857. Small-reader large-producer
p: .000488/.00635/.000488. Null trials were very short/noisy in the first run;
replication and reciprocal controls lengthened only null trials 16-fold. Pipe
losses were smaller. An initial smoke null penalty did not reproduce and is not
reported as an established effect.

This evidence rules out terminal parsing/rendering as a necessary cause of the
observed placement loss, and rules out a universally slow small-cache producer
as its sole explanation. Producer/reader pairing matters in this control. It
does NOT identify a kernel/cache-coherence/scheduler mechanism, or prove an
optimal placement policy. Cross-run sink medians are not paired policy gains.

Production follow-through: small-domain reader rejected
-------------------------------------------------------

L3, keeping parser/history on largest L3. This was not the earlier rejected
scheduler-managed reader. Same opt-out, allowed-mask intersection, homogeneous
machine no-op and macOS behavior. Producer, parser, buffering and HUP-drain
semantics unchanged. Fresh control/candidate built with identical flags/compiler.

credit recycling. No new broad-suite or cross-platform claim was made.

Audit, limitations and final state
---------------------------------
- All 972 transport trials replay, with raw hashes and byte/mask validation.
- Validator rejects altered hashes, wrong masks/counts, missing or duplicate
  trials, incomplete manifests. Negative validation is harness validation only.
- Exact named frozen script revisions and C sink source/executable preserved;
  final replay also succeeds with original /tmp sink absent. First missing-sink
  replay used a nonexistent manifest key and was fixed; no raw results changed.
- Host kernel.sched_schedstats=0. Original v1 summary printed runqueue fractions;
  do not interpret them. Final summaries report null (unavailable).
- Reciprocal run free-text note mistakenly says reader large; actual numeric
  sink_cpus and every measured sink_allowed field correctly say small. Its
  warm-up used large; measured trials used small. Final script fixes both,
  preserving the original frozen revision/manifest/raw data unchanged.
- Final harness closes spare parent read descriptor after readiness; final-smoke
  validates cleanup. Earlier descriptor lifetime is explicitly preserved in
  measured revisions. Production runtime code was not changed by harness fixes.
- Reader-role split removed after full rejection. affinity.rs/read_ahead.rs
  match selected source byte-for-byte. engine.rs has only an earlier explanatory
  comment correction relative to HEAD, no new runtime change.
- Exact selected release executable restored:
  SHA-256 d75cb26fb48120df841ff876ee110c1e45e5feb6c3996ddc90d01e681200805c.
- No quiet RTT or broad workspace tests rerun for rejected policies. No new
  latency improvement, comprehensive correctness, PGO or cross-platform claim.

Next necessary work
-------------------
Keep benchmark producer/comparator affinity unchanged. Do not promote the raw
transport sink policy. The all-metric objective still requires a Unicode gain
that survives fresh-control terminal pairs and a quiet-RTT guard, without losing
ASCII/region. Any follow-up topology policy must address BOTH producer->reader
and reader->parser links, not infer a default from a two-process synthetic sink.
