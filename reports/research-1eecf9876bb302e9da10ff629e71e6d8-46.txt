Iteration 46 — split UTF-8 scratch-buffer byte accounting

Concrete new finding
--------------------
A shared parser defect silently drops ASCII immediately after a completed split
UTF-8 scalar when the four-byte scratch buffer contains the beginning of the
next multibyte scalar (or an invalid byte). The error path emitted only one
scalar, then consumed the entire valid prefix. Return only the emitted scalar's
new bytes instead: c.len_utf8() - old_bytes. Subsequent ASCII is dispatched by
the normal loop. This also fixes early-termination consumed-byte reporting.

This was discovered by a direct upstream Term::input oracle while exploring
fused combining-mark overwrite. The speculative optimization was shelved,
removed in full, and not timed. The unchanged control failed the same direct
oracle. Fast/slow differential tests share the faulty parser and pass despite
this corruption, so their agreement cannot certify this class of correctness.

Logical review and limits
-------------------------
Only the valid-prefix error branch changes runtime behavior. It already clears
partial_utf8_len and emits one scalar; completed scalar size exceeds the old
partial byte count. Its copied trailing bytes are not lost because the caller's
slice remains authoritative and the next iteration reprocesses them. Existing
complete-buffer, still-incomplete and invalid-first-scalar paths are unchanged.
No unsafe code added. No layout, ownership, PTY reader, or renderer changes.

No benchmark sessions ran, no causal speedup is claimed, and no fresh production
executable was promoted. Ghostty comparison and memory/CPU/latency/resource gates
remain required on the same candidate production build before any championship
claim. No global acceptance command is bound; this is reported local correctness
progress, not a world-title or loop-completion claim.
