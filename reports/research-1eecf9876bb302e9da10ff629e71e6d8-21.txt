3. New concrete finding: cold C1 input can allocate without width lookup
-----------------------------------------------------------------------
Review identified that width_cache() moved before put_row's C1 stop condition.
A C1-only run crosses the 24-byte run threshold and reaches the row writer, but
printing stops before a scalar width is required. Thus the hoist can change
resource behavior even when all cells and width values remain correct.

This was tested, not merely left as a code-review conjecture. A distinct
post-screen protocol, cold-protocol.json, pins one instrumented diagnostic on
both frozen source arms. The same OnceLock is relocated to an observable module
static; initializer, atomic entries, access policy and row path are otherwise
unchanged in each arm. Each exact test runs in a new process, asserts the cache
is initially empty, feeds one whole stream and checks initialization before
running parser-state comparison. No performance series is repeated/replaced.

Stream                       control initialized    candidate initialized
16 U+0085 C1 scalars                false                    true
32 ASCII a bytes                   false                    false
16 U+754C wide scalars              true                     true

Six exact test processes pass. Cold source snapshots, binary identities and
per-process logs are retained. analyze-cold.py reconstructs the observations
and pins each log hash. Cache representation: 0x110000 = 1,114,112 AtomicI8
entries, one byte each, so payload is 1,114,112 bytes (1.0625 MiB). This is a
representation-derived allocation payload, not sampled allocator overhead,
RSS, retained process-memory delta, startup latency, energy or an allocation
rate estimate. Instrumentation can affect code generation; it is not used for
timing. The diagnostic does not reverse the failed performance gate. Neither
the instrumentation nor its extra ignored test remains in production source.

The warm minimum-of-five engine benchmark was not a first-use/resource oracle;
this is a specific reason an apparent micro-optimization needs separate cold
behavior review. No claim that a different lazy-hoist variant would succeed:
that would be a new prospective experiment, not a rescue of this one.

4. Retained regression and real negative control
-------------------------------------------------
The only retained Rust edit is speed::c1_row_runs_preserve_parser_state:
all 32 valid C1 scalars; C1-only and mixed z/wide/combining predecessors;
REP, cursor reports, alternate screen, no-wrap and colored templates; 3 screen
sizes; 7 read cuts including individual UTF-8 bytes and RUN_MIN 23/24/25 edges.
3 x 4 x 32 x 7 = 2,688 parser-differential scenarios. The oracle compares full
parser-visible grid/history/cursor/modes/reply state through the existing
plain_runs_first_difference helper, not just text output.

A deliberately defective compiled decoder maps valid C1 values to '?' instead
of their original scalar. The retained regression fails on actual cells at
3x2 / U+0080 / chunk 24, exit 101. Restored runtime passes the same test, exit 0.
Both executable hashes and exact logs are retained; checkpoint reruns this
contrast. This establishes sensitivity to this concrete decoder defect, not
all possible semantic bugs. It is a semantic guard, not a cache-allocation
regression test. The timing candidate's rejected resource behavior is not
misrepresented as something this test would catch.
